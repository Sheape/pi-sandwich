# Cross-platform CI and upstream-compatibility evidence

**Status:** research only; no testing policy or workflow is proposed here.
**Question:** What facts constrain testing a publishable Pi extension on x86-64 glibc Void Linux and Apple Silicon macOS, with Node >=22.19.0, Vite+ development tooling, and a Pi development pin plus runtime `*` peer dependency?
**Evidence cut-off:** 2026-07-28 (UTC+08:00). External links below are first-party documentation or the owning project's source at the stated revision.

## Direct answers

1. **Apple Silicon macOS is available on standard GitHub-hosted runners.** GitHub currently lists `macos-latest`, `macos-14`, `macos-15`, and `macos-26` as arm64 M1 macOS runner labels for both public and private repositories. The same document says community actions may be incompatible with arm64, nested virtualization is unsupported, and arm64 macOS has no static UUID/UDID. [GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners#standard-github-hosted-runners-for-public-repositories) ([limitations](https://docs.github.com/en/actions/reference/runners/github-hosted-runners#limitations-for-arm64-macos-runners), accessed 2026-07-28).
2. **GitHub does not offer a Void runner image.** Its standard Linux labels are Ubuntu; its published self-hosted Linux support list also does not include Void. A native Void host is consequently outside GitHub's documented hosted/self-hosted support matrix. [GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners#standard-github-hosted-runners-for-public-repositories); [self-hosted runner requirements](https://docs.github.com/en/actions/reference/runners/self-hosted-runners#supported-operating-systems) (accessed 2026-07-28).
3. **That does not mean every Void check must be manual or self-hosted.** Void officially publishes `linux/amd64` glibc OCI images, and GitHub supports a job container on an Ubuntu runner. This can exercise Void glibc userland on x86-64. It is not a booted Void system or a runit-init test; a native/manual or self-hosted Void machine remains the factual prerequisite for that class of test. [Void OCI images, `master`](https://github.com/void-linux/void-containers/blob/master/README.md); [GitHub container jobs](https://docs.github.com/en/actions/how-tos/write-workflows/choose-where-workflows-run/run-jobs-in-a-container) (accessed 2026-07-28).
4. **The supported Node baselines as of the cut-off are 22 and 24 LTS.** Node's release page lists v22.23.1 (Jod) and v24.18.0 (Krypton) as LTS, v26.5.0 as Current, and v25 as EOL; its release schedule gives v22 EOL as 2027-04-30 and v24 EOL as 2028-04-30. Thus the exact minimum `22.19.0` and the current 22/24 lines are independently meaningful; a v26 check is a current-line canary, not an LTS compatibility assertion. [Node releases](https://nodejs.org/en/about/previous-releases) (page state: v22.23.1/v24.18.0/v26.5.0, accessed 2026-07-28); [release schedule source](https://github.com/nodejs/Release/blob/main/schedule.json) (v22/v24/v26 dates, accessed 2026-07-28).

## 4. Pi package and extension compatibility surfaces

Pi's current package documentation, at commit `b6fb91e5b3a35a4361ae7d697d66eb7ed4dd9850` on 2026-07-28, establishes these install/test facts:

- `pi install` accepts npm, git, URL, and local sources; `pi -e` installs a package temporarily for a single run. [Pi packages: install/manage](https://github.com/earendil-works/pi/blob/b6fb91e5b3a35a4361ae7d697d66eb7ed4dd9850/packages/coding-agent/docs/packages.md#install-and-manage).
- A package may declare extensions in `package.json` under `pi.extensions`, or use the conventional `extensions/` directory. [Pi packages: creating/structure](https://github.com/earendil-works/pi/blob/b6fb91e5b3a35a4361ae7d697d66eb7ed4dd9850/packages/coding-agent/docs/packages.md#creating-a-pi-package).
- Third-party runtime dependencies belong in `dependencies`; Pi's core packages (`@earendil-works/pi-ai`, `@earendil-works/pi-agent-core`, `@earendil-works/pi-coding-agent`, `@earendil-works/pi-tui`, `typebox`) belong in `peerDependencies` with range `"*"` and must not be bundled. This directly supports the target peer-dependency shape. [Pi packages: dependencies](https://github.com/earendil-works/pi/blob/b6fb91e5b3a35a4361ae7d697d66eb7ed4dd9850/packages/coding-agent/docs/packages.md#dependencies).
- Pi's extension guide identifies the importable coding-agent API and describes extensions as TypeScript modules loaded by jiti; TypeScript therefore does not need a separate compilation step solely to load an extension. [Pi extensions: imports](https://github.com/earendil-works/pi/blob/b6fb91e5b3a35a4361ae7d697d66eb7ed4dd9850/packages/coding-agent/docs/extensions.md#available-imports); [extension loading](https://github.com/earendil-works/pi/blob/b6fb91e5b3a35a4361ae7d697d66eb7ed4dd9850/packages/coding-agent/docs/extensions.md#writing-an-extension).
- `pi update --all` updates Pi, packages, and reconciles pinned git refs; versioned npm specs and git refs are documented as pinned. [Pi packages: install/manage and sources](https://github.com/earendil-works/pi/blob/b6fb91e5b3a35a4361ae7d697d66eb7ed4dd9850/packages/coding-agent/docs/packages.md#install-and-manage).

The authoritative public surface for feature gates is the installed `ExtensionAPI`/extension type export. At the cited Pi snapshot, the type source contains named methods/events (for example `registerTool`, `registerCommand`, `on`, `resources_discover`, and `session_start`) but no declared extension API-version field or compatibility-negotiation method. [Pi extension types](https://github.com/earendil-works/pi/blob/b6fb91e5b3a35a4361ae7d697d66eb7ed4dd9850/packages/coding-agent/src/core/extensions/types.ts). That makes the requested capability/version fail-open behavior an extension-owned test concern: verify the installed API's needed member before using it, and verify installation/loading against both the development pin and a selected newer Pi build. This is an observation about the visible source surface, not a claim that Pi promises a stable version protocol.

## 5. Minimal native-dependency audit evidence

No product extension manifest exists in this revision, so there is no product runtime dependency tree to approve yet. The smallest audit that can be repeated once a package exists is:

1. Inspect the publish tarball (`npm pack --json`) rather than the repository checkout, and read its `package.json` for `dependencies`, `optionalDependencies`, `bundledDependencies`, `os`, `cpu`, and `libc` restrictions. npm documents `npm pack` as producing a `.tgz` package archive and supports JSON output. [npm pack](https://docs.npmjs.com/cli/v11/commands/npm-pack) (accessed 2026-07-28); [npm package.json](https://docs.npmjs.com/cli/v11/configuring-npm/package-json) (accessed 2026-07-28).
2. Install that tarball using each real target/runtime and run the smallest load probe. This catches a platform-selected optional binary that a lockfile review alone cannot execute. The Pi documentation requires ordinary runtime dependencies in `dependencies` and tells Pi to install npm/git packages with `npm install`. [Pi package dependencies](https://github.com/earendil-works/pi/blob/b6fb91e5b3a35a4361ae7d697d66eb7ed4dd9850/packages/coding-agent/docs/packages.md#dependencies).
3. If the tarball adds no native/bundled/optional dependency and the load probe uses only Node built-ins plus Pi peers, record that result and stop. If it adds one, record the exact package/version, selected OS/CPU/libc artifact, and whether the two target installs/load probes pass before broadening the audit.

This deliberately separates current development-tool native artifacts from publishable runtime artifacts: the repository lockfile already proves platform-selected **dev** packages exist, but it is not evidence that a future Pi package ships any.

## 6. Upstream drift and canary mechanics that GitHub/Pi actually provide

- GitHub Actions supports `schedule` cron workflows and `workflow_dispatch`; scheduled workflows use the latest default-branch commit, require the workflow file on the default branch, may be delayed or dropped at high load, and GitHub recommends avoiding the top of the hour. [GitHub events: schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule) (accessed 2026-07-28).
- A workflow with `workflow_dispatch` can be run from the Actions UI, CLI, or REST API; the workflow file must be on the default branch for the event to be triggerable. [GitHub manual workflow runs](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow) (accessed 2026-07-28). GitHub's REST endpoint is `POST /repos/{owner}/{repo}/actions/workflows/{workflow_id}/dispatches`, requires a `ref`, accepts up to 25 input properties, and requires Actions write permission for fine-grained tokens. [GitHub REST: create a workflow dispatch](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event) (API version shown by the page: `2026-03-10`, accessed 2026-07-28).
- Pi itself supplies a package update path: `pi update --all` updates Pi and packages, while pinned npm versions and git refs are not moved by package updates. [Pi package updates](https://github.com/earendil-works/pi/blob/b6fb91e5b3a35a4361ae7d697d66eb7ed4dd9850/packages/coding-agent/docs/packages.md#install-and-manage).

Those facts support a repeatable canary mechanism: a default-branch scheduled or manually dispatched job can select a Node/Pi input, install the published extension through `pi -e` or `pi install`, and report a load/capability result. The facts do **not** supply a GitHub-native way to make a scheduled run reliable to the minute, a hosted native Void runner, or a Pi-declared extension API compatibility number.

They characterize only that evidence-store prototype and those recorded environments; they do not establish package-install, Pi-extension, Vite+, or CI compatibility.
